# SM Reader: Specification (draft 2)

A simple, book-like EPUB reader inspired by Microsoft Reader (2000-2012): one page of text, centered on a dark surround, with adjustable fonts and page geometry.

## 1. Goals

- Recreate the look and feel of MS Reader's reading page and options.
- Read the user's existing EPUB files. EPUB stays the master storage format.
- Run on desktop and Android from one codebase.
- No account and no login required for the core app (v1). Cross-device sync is added later (v2) via the user's own XMPP account — see section 10 — not a third-party login provider.
- Books and reading data stay on the user's device unless the person opts into login-based sync.

## 2. Non-goals

- No ClearType or text-rendering toggle. The OS and browser control text smoothing.
- No Kindle location converter. Percentage is the shared position instead.
- No support for MOBI/AZW (binary formats). Convert to EPUB with Calibre.
- Highlights, notes, dictionary lookup and text-to-speech are later features.

## 3. Platform

- **Installable web app (PWA)**: static HTML, CSS and JavaScript, no build step.
- Hosted on GitHub Pages at `username.github.io/sm_reader` (repo name: `sm_reader`, "SM" as a reverse of "MS"). Only the app code is in the repo, never the books.
- **Relative paths everywhere**, so it works under a subpath. The service worker scope is set accordingly.
- `manifest.json` for installing, and a service worker for offline use.
- **EPUB library: foliate-js** (newer and more actively maintained than epub.js), stored in the repo, not loaded from a CDN.
- Works in Firefox, Chrome and other modern browsers on desktop and Android.

## 4. Library

- Import EPUB files with a file picker (multiple files allowed).
- Store books, covers, settings and positions in IndexedDB.
- Library view lists books with covers, title, author and progress percentage.
- Each book gets a **fingerprint** (hash of the file) plus the EPUB's own identifier, used to match the same book across devices.
- Nothing is uploaded anywhere.
- Note: browser storage can be cleared. Keep the original EPUB files backed up elsewhere.

## 5. Reading view

- One centered page on a dark surround. Paged reading, not scrolling.
- Click or tap the page edges (or use arrow keys, swipe) to turn pages.
- Small footer showing position: percentage with two decimals (and optionally location).
- Menu: table of contents, bookmarks, go to position, settings.
- On small screens (phones) the page fills the screen, as Reader did on the Pocket PC. The centered page with surround is for larger screens.

## 6. Themes

- Cream page (classic Reader look), white page, night mode (inverted).
- The surround is dark in all themes.

## 7. Typography

Font choice has three sources, all shown with a live preview:

1. **Bundled fonts** (open-source, in the repo). Default: **Jost** (Futura-like). Others: Outfit, Questrial, League Spartan, Literata, Atkinson Hyperlegible, and an optional dyslexia-friendly font. Futura itself is commercial and cannot be bundled.
2. **Installed font by name**: the user types a name (e.g. "Futura") and it is used if the device has it, with a fallback if not.
3. **Upload a font file** (.ttf, .otf, .woff2), stored in IndexedDB and added to the list.

Also:
- **Font size: a row of sensible numbered sizes** (e.g. 12, 14, 16, 18, 20, 24, 28, 32, 40, 48), shown as tappable numbers rather than named steps ("smallest".."largest") or a slider, plus a **custom field** where the user can type any number. This replaces Reader's named-step slider and sidesteps the "how many steps" question entirely, since the numbers are self-explanatory and unlimited via the custom field.
- Line spacing and text density.
- Defaults favor sans serif fonts.

## 8. Page geometry (Advanced settings)

- **Scale** (75% to 200%): a DPI-like multiplier that grows the page and text together.
- **Page width**: presets (narrow, medium, wide) and a slider. Controls characters per line.
- **Page height**: fit to screen (default) or a fixed proportion.
- **Margins** inside the page.
- **Surround**: amount of dark space, or none.
- Sizes are stored as proportions, not fixed pixels, so they scale to any screen.
- **Profiles**: named sets of settings (for example "Desktop", "Phone").
- **"Reader classic" preset**: values measured from the reference screenshots (section 12) — page height ≈ 88% of viewport height, page width:height ≈ 0.75 (3:4), text column ≈ 78% of page width (≈11% margin each side), equal top/bottom gap outside the page. Unlike Reader, SM Reader uses the same fixed number of size steps on every screen (Reader varied: 6 steps on the 20" screen, 5 on the 17").

Common settings (font, size, theme) stay on the main settings screen. Geometry is under "Advanced" to keep it uncluttered.

## 9. Position

### Saved internally (automatic resume on each device)

1. Book fingerprint
2. CFI (exact, used first when the file matches)
3. Chapter number plus character offset within the chapter
4. Short text snippet (about 30 characters) to correct small drifts
5. Overall percentage stored with 4 decimals

On load the app tries them in order of precision and uses the first that works.

### Shown to the user

- **Percentage with two decimals** (e.g. 42.73%), based on visible text characters, not file size or chapter count.
- Two decimals is about 30-60 characters in a typical novel, so it lands within a line or two.
- "Go to position" accepts a percentage (`42.73` or `42.73%`) or an optional location number (fixed-size chunks of visible text, for example 100 characters each, counted by Unicode characters, not bytes).
- Jumping lands at the start of the sentence or paragraph containing the point.

### Counting rules (must be identical on every device)

- Count visible text only, ignoring tags and hidden elements.
- Fixed handling of whitespace, footnotes and front matter.
- Count Unicode characters consistently (emoji and combined characters).

## 10. Sync

**Version 1 (no login, no backend, works from static GitHub Pages alone):**
- Percentage typed by hand between devices.
- Link or QR code containing book fingerprint and position.
- Export/import of a small file with positions, bookmarks and settings (also works as a backup).

**Version 2: XMPP self-messaging (primary plan — no third-party backend, reuses infrastructure the user already runs and trusts).**

GitHub Pages stays static in every option below; login/sync always needs *something* live behind it. XMPP is the pick because that "something" is a server the user already operates, not a new third party.

- **How it works:** the browser can't open a raw XMPP/TCP socket, but it can speak XMPP over a WebSocket (`wss://`), which most servers support (Prosody's `mod_websocket`, ejabberd's built-in support). A JS library such as Strophe.js handles the protocol. Needs a real TLS cert on the server, not self-signed, since the page is served over HTTPS.
- **Default account shape: self-messaging.** The user's own JID (e.g. `dbojan@jabber.fr`) logs in and sends a message to itself — a book title, author, and percentage position (e.g. "Alice's Adventures in Wonderland — 42.73%"). `from` and `to` being the same bare JID is valid XMPP; the server delivers and archives it normally. One account, one login stored in Settings, nothing else to create.
- **Optional alternative: a dedicated sender account** (e.g. `sm-reader@jabber.fr`) sending only to the user's own JID, kept as a mutual contact/roster subscription. Same one-to-one shape as the user's existing reminder setup (`dbojankuca@jabber.fr → dbojan@jabber.fr`), just for people who'd rather not store their main account's password in a browser. Offered as a setting, not the default.
- **Not a fan-out risk at this scale.** Blocking/rate-limiting is a concern for one account messaging *many different people's* servers, which this isn't — it's always a single fixed sender-to-recipient pair, whether self-messaging or the dedicated-sender variant. If this were ever shared with other people, the right pattern is each person runs their own sending account pointed at their own JID, never one shared bot for everyone.
- **Retrieving position on another device needs MAM (Message Archive Management, XEP-0313)** on the server. On load, the app queries the account's own archive for the most recent position message and offers "Continue from 42.73%, sent from your PC?" To check: confirm the user's server has MAM enabled.
- **Message Carbons (XEP-0280),** if enabled server-side, may duplicate the self-sent message into other connected sessions/clients — harmless for the app (it reads from the archive, not a live chat view), only visible if the user happens to be watching a regular XMPP client at the time.
- Credentials (JID + password) are stored in the browser on each device, used only to open the `wss://` connection to the user's own server. A dedicated low-privilege sending account, per the option above, avoids exposing the main account's password this way.

**Other options considered for v2 (not the current plan, kept here for reference):**

- **Firebase (Google Auth + Firestore).** Rejected: brings in a Google-account dependency the user wants to avoid, even though it would otherwise be the least-setup option (hosted, generous free tier, "Sign in with Google" needs no custom OAuth code).
- **Supabase (GitHub OAuth + Postgres).** An open-source Firebase-alternative; "Sign in with GitHub" would fit neatly since the user already has a GitHub account for Pages hosting. Still a third-party hosted service, even though it's not Google. Worth a second look if the XMPP route runs into blockers (e.g. no MAM support).
- **PocketBase (self-hosted).** A single Go binary bundling auth, database and file storage; the only option with zero third-party servers involved, but it means running and keeping something online continuously (a VPS, home server, Raspberry Pi) — more responsibility than reusing the existing XMPP server.
- **Cloudflare Workers + D1/KV.** Hosted like Supabase/Firebase, generous free tier, but lower-level — more custom code to write for the same result.
- **UnifiedPush.** Considered and set aside: it's an open push-notification standard, mainly relevant for native Android apps distributed outside Google Play that need a "wake up" signal without Firebase Cloud Messaging. SM Reader's sync is pull-based (checked on open or on demand), so push isn't needed. Would only become relevant if the app were later wrapped as a native Android app distributed outside the Play Store.

In all cases: conflict rule is the most recent position wins, with a prompt like "Continue from 42.73% on your phone?" Book files are never synced, only small notes (position, settings, metadata) — the same EPUB must be imported on each device. The rest of the app (import, reading, themes, fonts, geometry) is unaffected by whether sync is set up; it only replaces the manual v1 steps.

## 12. Reference: MS Reader screenshots (measured)

Source: MS Reader 2.1.1, screenshots supplied by the user, full screen, PNG, uncropped. Two monitors, both windowed Reader maximized.

**Measured page geometry** (measured directly from pixels, using the "row of a's" screenshots as a ruler):

| Item | 17" screen | 20" screen |
|---|---|---|
| Screen resolution | 1280x1024 (4:3) | 1680x1050 (16:10) |
| Page box (px) | 669 x 904 | 695 x 928 |
| Page width : height ratio | 0.740 | 0.749 |
| Page height as % of screen height | 88.3% | 88.4% |
| Top/bottom gap (px, equal both sides) | 60 / 60 | 61 / 61 |
| Page horizontal position | not centered on screen; sits right of the red sidebar, with a wider dark margin on the right than the sidebar's width on the left | roughly centered (492 left gap, 493 right gap) |
| Left/right text margin inside page | ~74-76 px each side (~11% of page width each) | ~74-78 px each side (~11% of page width each) |

**Key findings:**
- **The page keeps a fixed pixel size regardless of font size.** Changing font size changes how much text fits per page, never the page's own dimensions. This confirms the spec's approach: page geometry and text size are independent settings.
- **The page is sized to ~88% of the screen height** on both monitors, with equal top and bottom gaps, and a fixed aspect ratio close to 3:4 (0.74-0.75), not the screen's own aspect ratio. This is the single most useful number for the "Reader classic" preset.
- **The sidebar (red, on the left) is a fixed-width panel**, not part of the page or its surround; it holds "Go to" plus Library / Shop / Help / Settings / Return, and doesn't scale with the page.
- **Left/right text margins are ~11% of the page width per side**, i.e. the text column is about 78% of the page width. This is consistent across screens and font sizes.

**Font size steps** (from the Settings → Font Settings slider, "This window reflects your current font size selection" preview):
- **20" screen: 6 steps** — smallest, small, medium small, medium large, large, largest. Default/opened at "medium small" (position 3).
- **17" screen: 5 steps** (per your note) — Reader appears to offer one fewer step on the smaller/lower-resolution display. Default there was "medium" (position 3 of 5).
- Measured glyph pitch (20" screen, "a"-grid pages) scales roughly linearly across the 6 steps: about 10.2, 12.3, 13.2, 15.5, 17.4, up to 29.9 px per character at "largest" — i.e. largest is roughly 3x the character width of smallest, and the step sizes are not perfectly even (a bigger jump from "large" to "largest").
- Lines per page at the smallest size: ~39; at "largest": ~15. This is the range a "lines per page" slider should reproduce.

**Typography:**
- Body text: a serif ClearType font (Georgia-like), fully justified with hyphenation, first-line paragraph indents, no blank line between paragraphs.
- Chapter headings: centered, small caps for "CHAPTER I.", a serif title line below in a larger size.
- Book title in the header (top-left of page) and "by Author" / edition line on the title page: an italic serif, distinct from the body font, used only for titles/headers.
- No typeface choice was found anywhere in Settings. Reader 2.1.1 ships one body font and one display/title font; there is no font-family picker.

**"ClearType Settings" (Settings page 2) is a rendering calibration wizard**, not a font picker: it shows 5 renderings of the same paragraph and asks the user to pick the one that "looks best" (a subpixel-tuning step, like the old Windows ClearType Tuner). This confirms the earlier call: there's nothing here worth reproducing today, since browsers/OSes handle subpixel rendering themselves. A font *choice* (typeface), by contrast, is worth keeping, per section 7.

**Settings pages found** (4 total, paged via "Page 1 ▶ / ◀ Page N ▶"):
1. **Font Settings** — the font size slider and live preview described above.
2. **ClearType Settings** — rendering calibration (not reproduced; see above).
3. **Screen Settings** — "Full Screen off/on" and a "Visual Guides" checkbox (plus an activation-status note).
4. **Voice Settings** — "Verbosity" and "Highlight text as it is being read" (text-to-speech options; later-feature territory per section 11).

**"Go to" menu** (dropdown from the sidebar): Table of Contents, Most recent page, Begin reading, Begin playing, Furthest read, Annotations (greyed until any exist), About this title (greyed), Cover Image. Useful as the shape for SM Reader's own navigation menu.

**Table of Contents page**: a plain in-book page titled "Contents", chapter numbers as clickable links (teal) in a left column, chapter titles in a right column, no page numbers shown.

**Library view**: list rows, each with a small cover thumbnail, title, and an italic "Opened: <date>" or "(Not yet opened)" line. A left-hand "Sort" / "Search" panel sits where "Go to" appears on the reading page.

**Reading page footer**: centered "◂ N ▸" page-turn control with the current page number between the arrows; the whole control gets a light highlight box when focused/hovered.

**Annotation markers**: on an annotated page, small colored flag/highlight icons appear in the dark surround just outside the right edge of the page, one per marked paragraph, in various colors (presumably one per highlight color used). Confirms annotations are anchored to paragraphs and shown outside the page rather than inline in the margin.

**Not reproduced (later features / obsolete):** Shop, Buy eBooks/audiobooks, activation, text-to-speech and voice settings, ClearType calibration.

- **Goal:** a dictionary lookup for the selected word (a "later feature", section 11). Languages wanted: English, Serbian, Bosnian, Croatian.
- **Design direction (proposed, not approved):**
  - **User-imported dictionaries**, like font upload: the user picks a file once, it is stored in IndexedDB, lookups are fully offline. Nothing is added to the repo (a bundled dictionary would be a new data asset: explicit approval needed) and no word is sent anywhere (an online API was rejected: it needs a network and breaks the "stays on the device" principle).
  - **One common IndexedDB structure** (word, text of the definition or translation, dictionary name, languages) filled by one small importer per format; lookup does not care about the source format. First patch: **StarDict** (`.ifo`, `.idx`, `.dict` / `.dict.dz`); a second small patch could add **DICT** (dictd: `.index` + `.dict.dz`, FreeDict's native format); TSV / JSON for a personal word list is easy later. Mono- and bilingual dictionaries need no difference in the importer.
  - **Decompression:** `.dz` is gzip-based, the vendored `fflate` can unpack it (no new dependency). Many dictionaries are distributed as `.tar.bz2`: the app has no bzip2, adding it is a new dependency (explicit confirmation needed); extracting first or zipping them (the vendored `zip.js` reads zips) avoids it.

Dictionary loaded lazily (no startup cost). A simple suffix-stripping fallback for inflected forms ("wondered" finds "wonder").
